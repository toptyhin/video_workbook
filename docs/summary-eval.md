# Оценка моделей саммари (M14, T-14.1)

> Статус: **первичный протокол** (2026-10-27). Полный eval на 3–5 русских лекциях — открыт
> (см. `plans/14-summary-lfm.md` §5 T-14.1); здесь зафиксированы факты интеграционной проверки
> и известные ограничения.

## Конфигурация проверки

- Runtime: `resources/llama/llama-cli`, pinned **llama.cpp b11669** (`0.7.0-dev`, MIT), CPU.
- Модели (скачаны в рантайме, SHA-256 сверены с `backend/app/model_manifest.json`):
  - `KoarAI/LFM2.5-350M-Thinking-GGUF` — Q4_K_M, 229 314 528 Б; ревизия `be0063c4…`; LFM Open License v1.0;
  - `Qwen/Qwen2.5-0.5B-Instruct-GGUF` — Q4_K_M, 491 400 032 Б; ревизия `9217f5db…`; Apache-2.0.
- Параметры: `--jinja -c 4096 -t 4/6 --temp 0.2 --top-p 0.9 --repeat-penalty 1.05 -n 512`, GBNF
  `--grammar-file` (флаг `--json-schema` в b11669 падает с `Failed to initialize samplers`),
  `-rea off` для structured-стадий, инструкция — `-sys`, данные — `-p`, завершение — `-st`.
- Вход (rev2): 8 сегментов (~4 мин), тема «производные/интегралы»; проверка иерархического дерева:
  OUTLINE → SPLIT → динамические уровни (LFM — рекомендованная).

## Rev3: принудительное деление и описания (2026-10-27)

Проблема на реальном дереве (видео 24, 291.9 с, 95 сегментов, Qwen 0.5B, prompt v2): root OUTLINE дал
0.0 = 0–278.6 с (95%), split 0.0 → 0.0.0 = 0–219.6 с (75%) остался листом: модель ответила `split=false`
(два вызова ушли в fallback), а v2 не проверял размер блока. Rev3:
- force-split блоков > `max(45 с, 18% длительности)` (SPLIT-force → чанки ~800 токенов → fallback-halves);
- инвариант «дети = непрерывное покрытие родителя», невалидный split не принимается, `summary_levels` — только после валидации;
- промоушен гигантских top-level тем; детерминированный root «О чём видео + Темы»; дедупликация title/description.

Результат на том же видео: `max_level=4`, level1 — 21 блок, **max 44.6 с (15.3%)**, без пересечений,
полное покрытие; root перечисляет 8 тем; дублей title/desc у сиблингов нет. Время генерации ~4–5 мин на CPU.
Остаётся ограничение качества 0.5B: часть заголовков («Которую сильно рассчитываем там где») неудачна;
описания при этом уникальны и извлечены из содержания. Для более качественных формулировок нужен более крупный модель.

## Наблюдения и риски

1. **LFM2.5-350M-Thinking — community-модель** (официальной `LFM2.5-350M-Thinking` у Liquid AI нет).
   В UI она — рекомендованная (значок «Рекомендованная», без предупреждений), как решил пользователь.
2. **Qwen2.5-0.5B** на части входов переводит русский текст на английский, несмотря на ru-инструкции;
   для русского саммари это limitation, модель оставлена как альтернатива с переключением.
3. **Качество блоков у LFM 350M** нестабильно (возможны повторы/искажения в summary); структура дерева,
   покрытие и таймкоды при этом валидны благодаря парсеру/валидатору/fallback.
4. **Reasoning** в structured-стадиях отключён (`-rea off`); `summary.thinking=auto` учитывается
   пайплайном, но для JSON-стадий реального выигрыша не проверено.
5. Лицензии: LFM Open License v1.0 (порог выручки $10M, копия лицензии/notices); Qwen — Apache-2.0;
   llama.cpp — MIT; все — в `resources/THIRD-PARTY-NOTICES.md`.

```bash
bash scripts/fetch-llama-runtime.sh
# модели — через приложение («Настройки → Модели») или curl по URL из backend/app/model_manifest.json

# автотесты (fake, без сети/моделей)
cd backend && ../.venv/bin/python -m pytest -q tests/test_m14_*.py

# реальные модели (нужны resources/llama и .tmp/e2e-models)
VL_SUMMARY_REAL=1 VL_MODELS_DIR=$PWD/.tmp/e2e-models VL_LLAMA_CLI=$PWD/resources/llama/llama-cli \
  ../.venv/bin/python -m pytest -q tests/test_m14_real_model.py
```
