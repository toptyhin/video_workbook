# 03. M3 — Транскрипция

> Этап: M3 · Оценка: 3–4 дня · Зависит от: M1, M2 · Разблокирует: M4, M5
> Владелец: writer-core

## 1. Цель и границы

Этап превращает библиотеку в обрабатываемую: пользователь ставит файлы в очередь, приложение извлекает аудио через `ffmpeg`, распознаёт речь локально (`faster-whisper small`, INT8, CPU), пишет сегменты в БД и показывает прогресс. Воркер живёт в отдельном процессе, очередь строго последовательная, есть отмена и переобработка, работает восстановление после падения. После M3 файл проходит путь `queued → processing → done`, а `segments` заполнены и готовы к FTS-индексации в M4.

**Входит в этап:**
- `ffmpeg`-извлечение аудио → WAV 16 кГц mono (`pcm_s16le`), временные файлы в `$VL_DATA_DIR/tmp` с удалением после обработки.
- `faster-whisper small` INT8 CPU (`cpu_threads=6`, `vad_filter=True`, `word_timestamps=True`), авто-язык + форс `ru`/`en`, модель из `VL_RESOURCES_DIR`.
- Воркер в отдельном процессе `ProcessPoolExecutor(max_workers=1)`, event loop не блокируется.
- FIFO-очередь, статусы `queued/processing/done/error`, `/api/queue`, постановка в очередь, отмена, переобработка.
- SSE-прогресс: `video.progress`, `video.status`, `queue.state`; восстановление после разрыва SSE — опрос.
- Запись `segments` (start_ms/end_ms/text), `videos.headline/lang/model`, очистка временных WAV, `videos.error` при сбоях.
- Crash-recovery: `processing → queued` на старте и автоматический перезапуск очереди.
- Тесты с фейковым воркером (CI без модели) + slow-тест с реальной моделью; обновление документации.

**Не входит (границы):**
- FTS5-индексация `segments` и `/api/search` — M4 (M3 только пишет строки `segments`).
- `GET /api/videos/{id}/segments`, Range-стриминг, плеер, панель таймингов и визуализация — M5.
- Теги сегментов (`segment_tags`) и теги файлов — M6; пользовательские метки — M7.
- UI `「Обработать сейчас」` в панели таймингов — M5 (M3 даёт endpoint и кнопки в списке/тулбаре).
- Упаковка модели в `extraResources`, `scripts/fetch-model.sh` в релизе — M8; настройка модели через полный settings-диалог — M9.
- Параллельная обработка нескольких файлов запрещена (`TARGET.md` §9): всегда один воркер.
- Транскрипты в JSON рядом с видео не хранятся — только БД.

## 2. Предусловия

- M2 закрыт: watched folders работают, `videos` содержит проиндексированные файлы с `duration_ms`, список и статусы отображаются.
- `resources/ffmpeg/{ffmpeg,ffprobe}` доступны (dev — `./resources`, prod — `VL_RESOURCES_DIR`).
- Модель получена скриптом `scripts/fetch-model.sh` в `resources/models/faster-whisper-small` (CTranslate2, INT8); в CI модель отсутствует — используется фейковый режим.
- Python-зависимости: `faster-whisper` (подтягивает `ctranslate2`), `numpy`; отдельный `torch` не требуется.
- На dev-машине ≥ 8 ГБ RAM (рекомендуется 16 ГБ), доступны ≥ 6 аппаратных потоков; целевой лимит RAM — 3 ГБ (`TARGET.md` §8).
- Есть тестовые материалы: 1–3-минутный русский ролик, короткий англоязычный, битый файл, «тишина» без речи.

## 3. Решения

**D-03.1. Извлечение аудио — отдельный сервис.** Команда: `ffmpeg -hide_banner -nostdin -y -i <video> -vn -ac 1 -ar 16000 -c:a pcm_s16le <tmp>/<uuid>.wav`; таймаут 30 минут, при ошибке — `AudioExtractError` с кодом. Временный каталог `$VL_DATA_DIR/tmp` (A11/§7), очистка в `finally`; при старте приложения удаляются `*.wav` старше 24 часов (защита от прошлых падений, `TARGET.md` §8 «диск»).

**D-03.2. Один воркер-процесс, модель живёт в процессе.** `ProcessPoolExecutor(max_workers=1)` с контекстом `spawn`; каждый файл — отдельная задача пула. Модель загружается один раз при первом задании и кешируется в глобальной переменной процесса-воркера (повторная загрузка на каждый файл съела бы время старта). Главный процесс FastAPI получает результат через `concurrent.futures.Future`, не блокируя event loop (A6).

**D-03.3. Параметры распознавания.** `WhisperModel(model_dir, device="cpu", compute_type="int8", cpu_threads=6, num_workers=1)`; `transcribe(..., vad_filter=True, word_timestamps=True, beam_size=5, language=None|"ru"|"en")`. `word_timestamps` включается по `TARGET.md` §3.2, но в БД сохраняются только сегменты (контракт `segments` без слов). Язык: из настройки `language` (`00` §4.1 п.1); `auto` → `None` (детекция); фактический код ISO-639-1 сохраняется в `videos.lang`.

**D-03.4. Единицы прогресса — доля 0..1.** `videos.progress` хранит `min(0.999, last_segment.end / duration_s)`; 1.0 — только в статусе `done`; при постановке/отмене — 0. UI форматирует в проценты. SSE-события троттлятся до 2 в секунду на видео, запись в БД — не чаще 2 раз в секунду. Единицы зафиксированы в `00` §5 (доля `0..1`).

**D-03.5. Результат пишет главный процесс, а не воркер.** Воркер возвращает `{segments, lang, headline, model}` и не открывает SQLite. Запись — одна транзакция главного процесса: удаление старых сегментов этого видео, вставка новых, обновление `videos` (`status`, `progress`, `lang`, `model`, `headline`, `processed_at`, `error`). Это исключает блокировки БД из дочернего процесса и гарантирует атомарность результата.

**D-03.6. FIFO-очередь в памяти.** `TranscriptionQueue`: `deque` идентификаторов видео + один asyncio-цикл-потребитель. `enqueue` идемпотентен: файлы в `queued`/`processing` пропускаются (`skipped` с причиной), `done` требует явной переобработки. Порядок — порядок постановки; перезапуск приложения восстанавливает очередь из БД (D-03.9). Состояние наружу — `GET /api/queue`.

**D-03.7. Отмена — событие + жёсткий terminate.** На каждое задание создаётся `multiprocessing.Manager().Event()`; воркер проверяет его между сегментами и возвращает `Cancelled`. Если за 3 с воркер не завершился — процесс пула принудительно завершается (`terminate()`), пул пересоздаётся; приватный доступ к процессам пула изолирован в одном месте `services/queue.py` и покрыт тестом. Отмена `queued` выполняется мгновенно удалением из очереди. Итоговый статус — `pending` (не `error`).

**D-03.8. Crash-recovery.** Стартовая процедура (lifespan, до запуска цикла очереди): `UPDATE videos SET status='queued', progress=0 WHERE status='processing'`; затем все `queued` сортируются по `added_at` и автоматически ставятся в FIFO. Результат: после аварийного закрытия файл после рестарта либо уже `done`, либо `queued` и обрабатывается автоматически — это прямое покрытие `TARGET.md` §7 п.9.

**D-03.9. Ошибки не «зависают» в очереди.** Маппинг: `AudioExtractError` (ffmpeg), `ProbeError` (нет длительности), `ModelLoadError` (нет/битая модель), `MemoryError`, `Cancelled`, `UnexpectedError`. При ошибке: `status=error`, `videos.error` = краткий текст (≤ 1000 символов), полный traceback — в `backend.log` (ERROR), временный WAV удаляется, очередь переходит к следующему файлу; событие `backend.error` публикуется не чаще раза в 10 с.

**D-03.10. Переобработка.** `POST /videos/{id}/reprocess`: если файл сейчас обрабатывается — `409`; иначе удалить `segments` (каскад `segment_tags`), сбросить `error/progress/processed_at/headline`, статус `queued`, поставить в FIFO. Пользовательские метки и теги файла не трогаются — это данные пользователя, а не транскрипция.

**D-03.11. SSE — единственный путь прогресса, с fallback на опрос.** События `video.progress`, `video.status`, `queue.state` публикуются только из главного процесса через `EventBus` M1. Если SSE-соединение потеряно, UI опрашивает `GET /api/queue` и `GET /api/videos` раз в 5 с; при восстановлении SSE опрос прекращается.

**D-03.12. Тестируемость без модели.** Транскрипция инкапсулирована в `services/transcriber.transcribe()`; при `VL_FAKE_TRANSCRIBE=1` воркер выдаёт синтетические сегменты (по `duration_ms`), соблюдает отмену и шлёт прогресс. Это позволяет прогонять интеграционные тесты очереди/отмены/crash-recovery в CI без 500 МБ модели; тест с реальной моделью — маркер `slow`, по умолчанию пропускается.

**D-03.13. Настройки модели и языка.** Читаются из `/api/settings` (канонические ключи `whisper_model`, `language` — `00` §4.1 п.1) на момент старта задания, значения пишутся в `videos.model/lang`. Каталог модели — `<VL_RESOURCES_DIR>/models/faster-whisper-<model>`; если каталога нет — `ModelLoadError` и понятная ошибка в UI, без тихого fallback на другую модель (иначе `videos.model` станет ложью).

## 4. Изменения контрактов

### 4.1. API

| Метод | Путь | Статус | Что фиксирует этап |
|---|---|---|---|
| POST | `/api/videos/enqueue` | контракт `00` §4 | `200 {"queued":[1,3],"skipped":[{"id":2,"reason":"already_queued"}]}`; ставит в FIFO, статус `queued` |
| POST | `/api/videos/{id}/cancel` | контракт `00` §4; ответ — **новое** | `200 {"id":1,"status":"pending"}`; идемпотентно для `queued/processing`; `409` для `done/error`; `404` для неизвестного |
| POST | `/api/videos/{id}/reprocess` | контракт `00` §4; ответ — **новое** | `202 {"id":1,"status":"queued"}`; `409`, если файл уже обрабатывается |
| GET | `/api/queue` | контракт `00` §4 | `{"current":{"video_id":3,"title":"a.mp4","progress":0.34},"pending":[{"video_id":5,"position":1}],"total":1}` |
| GET | `/api/videos` | уточнение (элемент M2) | добавляются поля `lang`, `model`, `headline` |
| GET | `/api/events` | payload — контракт `00` A5 | см. §4.3 |

Формы ответов `enqueue`/`cancel`/`reprocess`/`queue` **ратифицированы** и внесены в `00` §4; SSE-payload — в `00` A5.

Коды ошибок: `400` — невалидный `ids` (пустой список, не-числа), `403` — нет доступа к пути файла, `404` — нет видео, `409` — конфликт состояния, `422` — схема pydantic.

### 4.2. БД

Новых миграций нет: используются колонки `lang`, `model`, `headline` (миграция 002, применена в M1) и таблица `segments` (001). Переходы статусов:

```text
pending → queued → processing → done
                          ↓
                        error (из любого места обработки)
queued|processing → pending      (отмена)
processing → queued              (crash-recovery при старте)
```

Запись результата: `headline` — первые ≤ 120 символов первого непустого сегмента (trim); `lang` — фактически определённый код (ISO-639-1); `model` — фактически использованная модель (`small` и т.п.); `processed_at` — ISO-8601 UTC в момент коммита транзакции.

### 4.3. SSE payload

| Событие | Payload | Частота |
|---|---|---|
| `video.status` | `{"video_id":3,"status":"processing","error":null}` | каждое изменение статуса |
| `video.progress` | `{"video_id":3,"progress":0.34}` | ≤ 2/с на видео |
| `queue.state` | `{"current_video_id":3,"current_progress":0.34,"pending_ids":[5,7],"total":2}` | каждое изменение очереди |
| `backend.error` | `{"code":"transcribe_failed","detail":"…","video_id":3}` | при ошибке, ≤ 1/10 с |

Все payload — в конверте M1 `{type, ts, payload}`; типы событий — из A5 (`00` §2), новых типов этап не вводит.

### 4.4. Настройки и внутренние контракты

| Ключ | Значения | Поведение M3 |
|---|---|---|
| `language` | `auto` (по умолчанию), `ru`, `en` | `auto` → детекция; `ru/en` → форс; канон ключей — `00` §4.1 п.1 |
| `whisper_model` | `tiny`, `base`, `small` (по умолчанию), `medium` | каталог `models/faster-whisper-<model>`; отсутствие — `ModelLoadError`; в офлайн-пакете есть только `small` (A11) |

Внутренний протокол воркера (не внешний контракт): входной dict задачи, `Manager().Event()` отмены, `Manager().Queue()` прогресса, возврат результата через Future. Значения `VL_TOKEN`/`VL_DATA_DIR`/`VL_RESOURCES_DIR` наследуются дочерним процессом из env.

## 5. Задачи

### T-03.1. Извлечение аудио, временные файлы и их очистка
**Файлы:** `backend/app/services/audio.py`, `backend/app/utils/paths.py` (tmp-хелперы), `backend/app/config.py` (пути), `backend/tests/test_audio.py`.
**Что сделать:**
1. `resolve_ffmpeg()` (resources → PATH), `extract_audio(video_path, tmp_dir) -> Path` с командой из D-03.1, таймаутом 30 мин и проверкой размера WAV > 44 байт.
2. Типизированные ошибки `AudioExtractError(code, detail)` (`ffmpeg_missing`, `ffmpeg_failed`, `empty_audio`, `timeout`), текст stderr обрезается до 500 символов для `videos.error`.
3. `cleanup_wav(path)` в `finally`; `cleanup_orphans(tmp_dir, max_age_hours=24)` — при старте приложения; удаление пустого tmp-каталога не требуется.
4. Тесты: реальный `ffmpeg` на коротком ролике (skip, если бинарника нет) — проверить `ffprobe`: 16 кГц, 1 канал, `pcm_s16le`; fake-ffmpeg с ненулевым кодом; таймаут; очистка после ошибки.
**Готово, когда:** WAV корректного формата создаётся и удаляется; при падении процесса файл подчищается на следующем старте; ошибки типизированы.
**Оценка:** 0.4 д.

### T-03.2. Воркер-процесс и распознавание (`faster-whisper`)
**Файлы:** `backend/worker/transcribe_worker.py`, `backend/app/services/transcriber.py`, `backend/app/config.py` (путь модели), `backend/tests/test_transcriber_unit.py`, `backend/tests/fake_whisper.py`.
**Что сделать:**
1. `transcribe_worker.transcribe_job(payload, cancel_event, progress_queue) -> dict` — точка входа процесса пула; загрузка модели по D-03.3 с кешем в глобальной переменной; путь модели из `<VL_RESOURCES_DIR>/models/faster-whisper-<model>`; `ModelLoadError` при отсутствии каталога.
2. Итератор сегментов: на каждом сегменте проверка `cancel_event.is_set()` → ранний возврат `{"cancelled": true}`; блок прогресса `progress_queue.put_nowait({"video_id":…, "progress":…})` не чаще 2/с; сбор `segments` в `start_ms/end_ms/text`.
3. Признак `vad_filter=True`, `word_timestamps=True`; `language` из настроек; фактический язык из `info.language`; `headline` из первого непустого сегмента.
4. Фейковый режим `VL_FAKE_TRANSCRIBE=1`: синтетические сегменты по `duration_ms` (например, 5 сегментов с шагом), искусственная задержка 100 мс на сегмент, соблюдение отмены и прогресса.
5. Unit-тесты: фейковый режим → структура результата, отмена посреди итерации, прогресс монотонен; `slow`-тест реальной модели на 30-секундном фрагменте (ru и en) — маркер `slow`.
**Готово, когда:** фейковый режим покрыт тестами; реальная модель грузится из resources и возвращает непустые сегменты на тестовом ролике; `cpu_threads=6` и INT8 подтверждены в логе при загрузке модели.
**Оценка:** 0.5 д.

### T-03.3. FIFO-очередь, `ProcessPoolExecutor` и API очереди
**Файлы:** `backend/app/services/queue.py`, `backend/app/routers/queue.py`, `backend/app/routers/videos.py` (`/enqueue`), `backend/app/main.py` (lifespan: запуск цикла очереди), `backend/tests/test_queue.py`, `backend/tests/test_api_queue.py`.
**Что сделать:**
1. `TranscriptionQueue`: `deque`, `current`, `asyncio.Lock`, `enqueue(ids)`, `cancel(id)`, `_run_loop()`; `ProcessPoolExecutor(max_workers=1, mp_context=spawn)`; `submit` задания, `await asyncio.wrap_future(future)`; пересоздание пула при фатальном сбое.
2. `enqueue`: фильтрация `queued/processing`, `done` без флага — пропуск; смена статуса на `queued`, `progress=0`, `error=NULL`; публикация `video.status`/`queue.state`.
3. `POST /api/videos/enqueue` и `GET /api/queue` (шейпы §4.1); валидация `ids` (непустой список, только существующие); `404` при неизвестном id? — решение: неизвестные id попадают в `skipped` с причиной `not_found`, общий ответ `200`.
4. Цикл обработки: `processing` → воркер-задача → `done`/`error`; после завершения — следующий из очереди; `queue.state` при каждом переходе.
5. Тесты (фейковый воркер): FIFO-порядок двух файлов, пропуск дублей, `/api/queue` отражает текущий/ожидающих, один воркер-процесс одновременно (`ps`-подобная проверка через внутренний счётчик).
**Готово, когда:** два файла проходят последовательно; `/api/queue` корректен в каждом состоянии; event loop отвечает на `/api/health` во время обработки (< 300 мс).
**Оценка:** 0.5 д.

### T-03.4. Поток прогресса: воркер → БД → SSE
**Файлы:** `backend/app/services/queue.py` (poller), `backend/app/services/events.py` (throttle), `backend/tests/test_progress.py`.
**Что сделать:**
1. Poller-задача в главном процессе читает `Manager().Queue()` прогресса, обновляет `videos.progress` не чаще 2 раз/с.
2. Публикация `video.progress` с троттлингом 2/с на видео; финальное событие `progress=1.0` при `done`; сброс на 0 при `queued`/отмене.
3. Ограничение роста очереди прогресса: `put_nowait` + отбрасывание устаревших значений для того же видео.
4. Тесты: фейковый воркер с 5 сегментами — прогресс монотонно растёт, 0 ≤ p < 1 во время обработки, 1.0 после; количество событий ≤ 2/с; SSE-поток содержит `video.progress`; БД-значение совпадает с последним событием.
**Готово, когда:** прогресс виден в SSE и БД; троттлинг подтверждён тестом; отмена обнуляет прогресс.
**Оценка:** 0.4 д.

### T-03.5. Сохранение результата: сегменты, `headline`, `lang`, `model`
**Файлы:** `backend/app/services/queue.py` (persist-часть), `backend/tests/test_persist.py`.
**Что сделать:**
1. Транзакция результата (D-03.5): удалить сегменты видео, вставить новые (`start_ms`/`end_ms` целые, `text` trim, пустые пропускаются), обновить `videos` (`done`, `progress=1`, `lang`, `model`, `headline`, `processed_at`, `error=NULL`).
2. Валидация сегментов: `end_ms > start_ms`, `start_ms >= 0`; при нарушении — ошибка задания `invalid_segments` (в `videos.error`), транзакция откатывается.
3. Пустая транскрипция (нет речи/VAD отфильтровал всё) — `done` с 0 сегментов, `headline=NULL`, лог WARNING; UI M5 покажет «Транскрипция пуста».
4. Ошибка внутри транзакции (симуляция в тесте) → `status=error`, `videos.error`, старые сегменты не тронуты (для `reprocess` — удалены заранее, поэтому пусто).
5. Тесты: 3 сегмента записаны и читаются SQL; `headline` ≤ 120 символов; повторная переобработка заменяет сегменты, не дублирует.
**Готово, когда:** после `done` `segments` содержат корректные интервалы; `videos.lang/model/headline` заполнены; атомарность подтверждена тестом.
**Оценка:** 0.4 д.

### T-03.6. Отмена, переобработка и crash-recovery
**Файлы:** `backend/app/services/queue.py` (cancel/reprocess/recovery), `backend/app/routers/videos.py` (`/cancel`, `/reprocess`), `backend/app/main.py` (startup-процедура), `backend/tests/test_cancel.py`, `backend/tests/test_crash_recovery.py`.
**Что сделать:**
1. `Manager().Event()` на задание; проверка отмены между сегментами; grace 3 с; принудительный `terminate()` процесса пула и пересоздание пула (приватный API — в одном месте, комментарий с обоснованием).
2. `POST /api/videos/{id}/cancel`: `queued` — удалить из deque, статус `pending`, `queue.state`; `processing` — событие + ожидание; `done/error` — `409`; неизвестный — `404`; идемпотентность (повторный cancel `pending` → `200`).
3. `POST /api/videos/{id}/reprocess` (D-03.10): удаление сегментов, сброс полей, `queued`, постановка в FIFO; `409` для `processing`.
4. Crash-recovery на старте (D-03.8): `processing → queued`, авто-постановка всех `queued` по `added_at`; выполняется до старта цикла очереди.
5. Тесты: отмена `queued` и `processing` (фейковый воркер, проверка времени ≤ 3.5 с и отсутствия зомби); повторный cancel; reprocess чистит сегменты и сохраняет `annotations`/`video_tags`; рестарт приложения с `processing`-строкой → `queued` и затем `done`.
**Готово, когда:** отмена прекращает работу за ≤ 3.5 с; после перезапуска «застрявший» файл обрабатывается; `TARGET.md` §7 п.9 подтверждён вручную.
**Оценка:** 0.4 д.

### Открытые вопросы

1. **Единицы `videos.progress`** нигде не зафиксированы (`REAL DEFAULT 0`). Принято 0..1; UI форматирует в проценты. Подтвердить для `00` §5 и M5 (прогресс-бар в панели таймингов).
2. **Шейпы ответов** `/enqueue`, `/cancel`, `/reprocess`, `/queue` не зафиксированы в `00` §4 (только путь и назначение). Предложены в §4.1; требуется согласование для M5/M9.
3. **Payload SSE** не зафиксирован (только имена событий в A5). Предложены в §4.3; от них зависят `useSSE` (M1), UI M3 и M5.
4. **Отмена текущего задания vs `ProcessPoolExecutor`**: A6 требует `ProcessPoolExecutor(max_workers=1)` и `terminate()` с grace 3 с. У `ProcessPoolExecutor` нет публичного API завершения одной задачи, поэтому используется приватный доступ к процессам пула, изолированный в `services/queue.py`. Альтернатива — долгоживущий `multiprocessing.Process` с командной очередью (отклонение от A6). Требуется решение Lead'а.
5. **Автозапуск очереди после crash-recovery**: TARGET требует лишь статус `queued` после рестарта; принято автоматически возобновлять обработку всех `queued`. Если нужно ожидание явного действия пользователя — изменить в M9 (настройка/поведение).
