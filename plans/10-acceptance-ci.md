# 10. M1–M9 — Приёмка и CI (сквозной этап)

> Этап: сквозной (обслуживает M1–M9) · Оценка: 2.5 дня · Зависит от: готовности фич M1–M7, артефактов M8, полировки M9 · Разблокирует: релиз-кандидат, финальную приёмку
> Владелец: writer-search

## 1. Цель и границы

Файл описывает сквозной контур качества: матрицу приёмки `../TARGET.md` §7, CI-конвейер в `ubuntu:22.04`, скрипты приёмки, проверку на чистой системе, замеры ресурсов, offline-контроль, чек-лист релиз-кандидата и регресс-матрицу перед M8. Контур запускается по мере готовности этапов и целиком — перед релизом; этап не имеет собственного product-релиза и завершается отчётом в `docs/acceptance.md` + артефактами прогона.

**Что делает этап:**
- матрица 10 критериев `../TARGET.md` §7 → конкретная проверка, инструмент, этап, тип (авто/ручной) и статус;
- `scripts/ci.sh` в Docker `ubuntu:22.04`: `ruff`, `pytest`, `vitest`, `tsc --noEmit`, сборка артефактов, smoke-запуск, контрольные суммы;
- `scripts/acceptance.sh`: полуавтоматический прогон критериев на dev-сборке и на релизном артефакте;
- `docs/acceptance.md`: протокол прогонов, результаты, отклонения;
- чистые Ubuntu 22.04/24.04 (VM или контейнер с GUI-зависимостями) без Python/ffmpeg у пользователя;
- замеры RAM (≤ 3 ГБ при транскрипции, ≤ 1.5 ГБ в покое), CPU (воркер ≤ 6 потоков), диска (tmp WAV удаляются, логи 10 МБ × 5);
- offline-проверка: 0 исходящих запросов (`ss -tp`, `tcpdump`);
- чек-лист релиз-кандидата и регресс-матрица перед M8;
- ручные сценарии приёмки для меток и поиска по меткам.

**Чего этап не делает (границы):**
- не реализует продуктовые фичи и не правит их контракты — дефекты фиксируются в отчёте и уходят владельцам этапов;
- не занимается упаковкой (PyInstaller/electron-builder — M8), только проверяет уже собранный артефакт;
- не заменяет ручную приёмку на чистой ВМ: автоматизация покрывает установку, запуск, API и headless-сценарии, GUI-критерии подтверждаются человеком по чек-листу;
- не настраивает внешние CI-сервисы (GitHub Actions и т.п.) — только локальные скрипты, пригодные для запуска на любом раннере;
- не меняет `TARGET.md`, `PLAN.md`, `00-conventions.md`; расхождения — в отчёт и «Открытые вопросы» §4.

**Готово, когда:** `scripts/ci.sh` зелёный на чистом контейнере; `scripts/acceptance.sh` формирует отчёт; `docs/acceptance.md` содержит матрицу с результатами и подписанный чек-лист RC; все 10 критериев §7 имеют подтверждённый результат либо явно оформленное исключение.

## 3. Решения

**D1. Один вход — `scripts/ci.sh`, стадии отдельными флагами.** `--stage=lint|test|build|smoke|artifacts|all` позволяет локально прогонять только нужное и переиспользовать стадии в `scripts/acceptance.sh`. Любая упавшая стадия — ненулевой код выхода, лог в `dist/ci/<stage>.log`.

**D2. Один базовый образ `ubuntu:22.04`, CI — надстройка над build-образом M8.** A10 требует совместимости с целевой ОС; тесты и сборка идут на glibc 2.35. `packaging/docker/Dockerfile.build` (M8, digest зафиксирован, Python 3.11, Node LTS, `libgomp1`, `patchelf`) — единственный базовый слой; `packaging/docker/Dockerfile.ci` (M10) добавляет `ruff`, `pytest`, `vitest`, Playwright-зависимости, `xvfb`, `tcpdump`. Дублирования сборки нет: стадия `build` вызывает `scripts/make-release.sh` (M8), а не свои команды electron-builder. Альтернатива (тесты в `python:3.11-slim`) отклонена: glibc/Debian расходятся с прод-артефактом.

**D3. Отдельные стадии «сборка» и «smoke», доступные после M8.** Сборка (`make-release.sh`: Vite, PyInstaller `--onedir`, electron-builder `.deb` + `.AppImage`) не должна маскировать падение тестов; smoke запускает уже собранный артефакт и проверяет `/api/health` и старт окна. Это ловит класс ошибок «собралось, но не запускается», который не виден pytest. До готовности M8 конвейер гоняет `lint|test` и smoke на dev-сборке, а `build|artifacts` помечают «требуется M8» (код 2, не 1).

**D4. GUI в контейнере — через `xvfb-run`, sandbox выключается только в тест-обвязке.** В `.deb` sandbox Chromium остаётся включённым (TARGET §9); для контейнера используем `xvfb-run -a` и `--no-sandbox` как аргумент *запуска теста*, а не как настройку приложения. GUI-критерии, которые нельзя проверить достоверно (появление окна, звук, fullscreen), подтверждаются вручную на VM с GNOME.

**D5. Старт окна измеряется по логу приложения, а не по секундомеру.** Electron-main пишет в `electron.log` строку `startup.window_visible` с `elapsedMs` от старта процесса. `scripts/measure-startup.sh` запускает приложение под `xvfb-run`, ждёт строку, берёт медиану из 5 запусков. Это воспроизводимо и не зависит от реакции человека; критерий §7 п.1 «< 5 с» проверяется по этому числу.

**D6. Ресурсы измеряются по процессному дереву, а не по одному PID.** Electron — это несколько процессов, транскрипция — дочерний процесс с потоками. `scripts/measure.sh` опрашивает `ps --no-headers -o rss= -C videolessons,python3` каждую секунду в течение сценария, суммирует RSS по дереву (тот же прогон повторяется 3 раза, берётся медиана пика), а для памяти контейнера дополнительно читает `memory.peak` cgroup v2. Пороги: пик ≤ 3 ГБ (транскрипция `small`), простой ≤ 1.5 ГБ. CPU: `ps -L` по процессу воркера → число потоков; `faster-whisper` запускается с `cpu_threads=6`, допускается ≤ 6 потоков воркера + служебные ffmpeg.

**D7. Замеры — сценарий, а не «на глаз».** Фиксированные сценарии: (S1) простой 60 с после запуска; (S2) транскрипция 10-минутного файла; (S3) открытие видео + скраббинг 60 с; (S4) поиск 20 запросов. Для каждого — RAM/CPU/время; результаты — в отчёт. Порог считается пройденным по медиане 3 прогонов, отклонения > 15 % между прогонами — пометка «нестабильно».

**D8. Offline-проверка — два независимых инструмента.** `ss -tunp` опрашивается раз в 2 с в течение всего сценария (ловим установленные соединения), параллельно `tcpdump -i any -nn 'not host 127.0.0.1 and not host ::1'` пишет pcap. Критерий: 0 пакетов к внешним адресам за 15 минут полного сценария (включая запуск, индексацию, транскрипцию, поиск, метки). Разрешён только loopback; DNS-запросы к внешним серверам — тоже нарушение (проверяем `port 53` отдельно). Electron `autoUpdater` и телеметрия не подключаются (проверка кода + отсутствие исходящих).

**D9. `scripts/acceptance.sh` — полуавтомат с машинным отчётом.** Автоматизируется то, что не требует глаз: установка `.deb` в чистый контейнер, `/api/health`, API-сценарии (индексация, поиск, метки), восстановление после перезапуска (перезапуск процесса + проверка БД/`localStorage` через CDP), offline, ресурсы. Ручные шаги печатаются чек-листом с шагами и ожидаемым результатом; отчёт пишется в `dist/acceptance/report.json` и `report.md`, `docs/acceptance.md` ссылается на прогон и фиксирует подпись.

**D10. `docs/acceptance.md` — протокол, а не маркетинг.** Таблица по 10 критериям с колонками «критерий / проверка / результат / дата / артефакт (лог, скриншот)», отдельный раздел ручных сценариев меток и тегов, раздел «Отклонения» с номером issue/плана. Отчёт без «пройдено» без ссылки на лог или скриншот не принимается.

**D11. Регресс-матрица перед M8.** Прогоняется после упаковки: каждый этап M1–M7 имеет 2–4 быстрые проверки, которые не зависят от свежих фич. Матрица в §7, исполнение — `scripts/acceptance.sh --regress`, результат обязан быть зелёным до начала M8.

**D12. Чистая система — две ОС, два уровня.** 22.04 — целевой минимум (A10); 24.04 — проверка «свежая LTS». Для обеих: нет Python/ffmpeg в системе (проверить `command -v python3 ffmpeg` до установки и после — не должно появиться системных пакетов), установка `.deb` из `dist/`, запуск, транскрипция, повторный запуск. 26.04 (TARGET §7 п.1) проверяется по возможности на момент RC; если VM недоступна — фиксируется как известное ограничение с датой проверки.

**Решения по открытым вопросам (ратифицировано Lead'ом):**
1. **VM 22.04/24.04 (и 26.04):** критерий §7 п.1 остаётся «ручной, ожидает» до предоставления инфраструктуры; в `docs/acceptance.md` фиксируется статус и конфигурация.
2. **`--no-sandbox`:** допустим только как аргумент запуска в тест-контейнере; в `.deb`/AppImage sandbox остаётся включённым (`TARGET.md` §9).
3. **`--acceptance-mode`:** не вводится; приёмка через env `VL_DATA_DIR`/`VL_TOKEN` и UI-автоматизацию.
4. **Порог старта:** медиана 5 запусков на фиксированной конфигурации 2 vCPU / 4 ГБ; конфигурация и результат — в отчёте.
5. **Артефакты прогонов:** pcap/логи — в `dist/` (gitignored) и CI-артефакт; в git — только `docs/acceptance.md` со ссылками.

**Не применимо: этап без изменений UI.** Приёмка выполняется через существующий интерфейс; новых экранов, компонентов и хоткеев этап не добавляет. Для ручных сценариев ниже зафиксированы маршруты в UI (чтобы проверяющий не импровизировал).
